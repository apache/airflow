KubernetesExecutor task pods no longer receive the metadata database credentials, and Celery workers drop them when a separate result backend is configured.

``AIRFLOW__DATABASE__SQL_ALCHEMY_CONN`` and ``AIRFLOW_CONN_AIRFLOW_DB`` are removed from KubernetesExecutor task pods and, when a result backend is set with ``data.resultBackendConnection``, ``data.resultBackendSecretName`` or ``config.celery.result_backend``, the Celery worker container. Without such a result backend the Celery worker keeps ``AIRFLOW__DATABASE__SQL_ALCHEMY_CONN``, because Celery derives its result backend from it. With KEDA the worker keeps both variables. Worker Kerberos sidecars lose ``AIRFLOW_CONN_AIRFLOW_DB``, and from Airflow 3.4.0 also ``AIRFLOW__DATABASE__SQL_ALCHEMY_CONN``. A separate result backend needs ``apache-airflow-providers-celery`` 3.12.4 or newer. The API server no longer receives ``AIRFLOW_CONN_AIRFLOW_DB``, so the ``airflow_db`` connection cannot be looked up through the Execution API. Task code that relied on either variable or on the ``airflow_db`` connection needs its own connection. Airflow falls back to SQLite in containers without the connection and fails at import on engine arguments SQLite does not accept, so set ``sql_alchemy_engine_args`` through ``config.database``, where the chart clears it for those containers, rather than through ``env``.
