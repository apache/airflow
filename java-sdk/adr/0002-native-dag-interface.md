# ADR-0002: Native Java Dag — Interface Design

## Status

Proposed

## Context

A Dag authored with no Python stub file has no `@task.stub` call site to declare its graph, so
Java itself must express the graph, the Dag/task configuration, and the task bodies. This ADR is
scoped to what that Java call site looks like for a user. It shares the injectable
`client`/`context` question raised in [ADR-0001](0001-mixed-lang-dag-interface.md), and shares the
protocol substrate (the argument-binding spec) with
[`airflow-core/adr/lang-sdk/0007-taskflow-across-language-boundary.md`](../../airflow-core/adr/lang-sdk/0007-taskflow-across-language-boundary.md).

## Decision

### Annotation based

A task method takes only its data. `Client` and `Context` come from getters on `Tasks`, the SDK base
class, so each method's real signature is exactly what the wiring expression composes:

```java
@Builder.Dag(id = "java_etl", schedule = "@daily")
public class EtlPipeline extends Tasks {

  @Builder.Task(id = "extract", retries = 2)
  public long extract() {
    return ((Number) getClient().getVariable("row_count")).longValue();
  }

  @Builder.Task(id = "transform")
  public long transform(long extracted) {
    getClient().setXCom("scaled_in", getContext().runId);
    return extracted * 2;
  }

  @Builder.Task(id = "load")
  public void load(long transformed) {
    log.log(INFO, "Loaded {0} for run {1}", transformed, getContext().runId);
  }

  @Wiring
  void depends() {
    load(transform(extract()));
  }

  public static void main(String[] args) {
    Bundle bundle = new Bundle().register(EtlPipeline.class);
    Server.create(args).serve(bundle);
  }
}
```

`javac` type-checks `load(transform(extract()))` against the methods that will actually run, because
`long -> long -> void` is already their real shape. `@Wiring` is read, never called: the processor
turns the call expression into Dag edges, and no task body runs at Dag-parse time.

The result is the Dag below, equivalent to writing the interface-based form by hand:

```java
// Generated by the Airflow Java SDK annotation processor. Do not edit.
public final class EtlPipeline_Dag {

  public static Dag dag() {
    Dag dag = new Dag("java_etl").config("schedule", "@daily");
    TaskRef extract = dag.task("extract", Extract.class).config("retries", 2);
    TaskRef transform = dag.task("transform", Transform.class).after(extract);
    dag.task("load", Load.class).after(transform);
    return dag;
  }

  public static final class Transform implements Task {
    @Override
    public void execute(Context context, Client client) throws Exception {
      TaskArgs args = TaskArgs.of(context);
      long extracted = args.require(0, Long.class);
      EtlPipeline tasks = new EtlPipeline();
      tasks.bind(context, client);
      client.setXCom(tasks.transform(extracted));
    }
  }

  // Extract and Load follow the same shape.
}
```

`bind(context, client)` is what `getClient()` and `getContext()` return for that invocation, and a
getter called with nothing bound throws.

### Interface based

```java
Dag dag = new Dag("java_etl").config("schedule", "@daily");

TaskRef extract = dag.task("extract", Extract.class).config("retries", 2);
TaskRef transform = dag.task("transform", Transform.class).after(extract);
TaskRef load = dag.task("load", Load.class).after(transform);

load.before(dag.task("notify", Notify.class));
```

`dag.task(id, class)` registers the task as it creates it and hands back a `TaskRef`, so there is no
second `addTask(...)` call to forget. `before` and `after` are the edge verbs, variadic and mirror
images of each other — Java's spelling of Python's `>>` and `<<` — and `.config(key, value)` carries
Dag and task configuration.

### Registering and serving

Both surfaces produce a `Dag`, and a `Bundle` is what the server serves — create it, register, serve:

```java
public static void main(String[] args) {
  Bundle bundle = new Bundle()
      .register(EtlPipeline.class)   // annotation based: the user's own annotated class
      .register(dag);                // interface based: the Dag built above

  Server.create(args).serve(bundle);
}
```

An annotated Dag registers as the class the user wrote — the same class the annotations are on — so
there is no second name to learn or keep in sync.

Nothing is constructed at registration. Task classes are instantiated per task-instance
run ([ADR-0001](0001-mixed-lang-dag-interface.md)), and the Dag definition itself is read once, at
registration, without running a task body.

One bundle carries native Dags and mixed-language stub handlers alike
([ADR-0001](0001-mixed-lang-dag-interface.md)), so one process serves both.

## Alternatives

- **Keeping `Client`/`Context` as task parameters.** The wiring expression would then compose
  different signatures than the ones that run, so a bridge has to exist somewhere: either the wiring
  names the injectables (`load(ctx, transform(client, ctx, extract(client)))`), or the user extends a
  generated supertype holding data-only overloads — a name in user source that an IDE cannot resolve
  until the first build. Getters remove the mismatch instead of bridging it.
- **Capturing the graph at run time** by generating a subclass that overrides each task
  method to record an edge and return a placeholder. Virtual dispatch makes the inherited `depends()`
  call the overrides, so no task body runs — but a `long` return carries no identity, so a result
  stored in a local and used twice cannot be attributed to its producer. Reading the tree has no
  such blind spot.

## Consequences

- Two authoring surfaces (annotation, interface) both flow into the same `Dag`/`TaskRef` model, and
  the annotation surface generates exactly the interface-based calls a user could have written.
- The annotation surface generates only what runs — a Dag definition and one `Task` per method — and
  nothing whose only purpose is to make user code compile.
- A task method is plain Java with a real signature, so nothing about the authoring surface exists
  only to satisfy the compiler: no twin class, no `In<T>`, no `TaskRef<T>` wrapper.
- Native tasks keep `@Builder.Task`, while the mixed-language surface moves to
  `@Builder.StubHandler` ([ADR-0001](0001-mixed-lang-dag-interface.md)), so an annotation names
  which of the two things a method is.
- The interface-based surface wires edges through object references (`after(extract)`) rather than
  through compile-time-generated calls, so it needs no tree reading and works under any compiler.

## Appendix: Implementation Notes

- The processor walks the `@Wiring` body's syntax tree and emits one `after` edge per nested call,
  ignoring arguments whose static type is `Client` or `Context`, so the expression above becomes
  `extract -> transform -> load`. A task result held in a local and passed to two downstream tasks is
  ordinary tree analysis, and a call that is not a task method is a compile error reported on its own
  source line through `Messager`.
- `com.sun.source.util.Trees` is exported by `jdk.compiler` and is stable to use from a processor,
  but it is javac's tree model: a processor built on it does not run under a compiler with its own
  model, such as ecj. Gradle drives javac here, so this is a constraint to record rather than one to
  solve.
- A task method is an ordinary method with a real return type, so a test subclasses the Dag class and
  overrides `getClient()`/`getContext()`, with no `In<T>` to unwrap.
- Resolving a task result held in a local is required, not optional. `long e = extract(); fanin(e, ping());`
  reads as an identifier rather than a call, and a walker that only follows nested invocations drops
  the `extract -> fanin` edge **silently**. The processor resolves an identifier through the local's
  initializer, and rejects an argument it cannot attribute rather than emitting an incomplete graph.
- **The getters need no thread-local.** `bind` sets a field on `Tasks`, and the generated code already
  constructs the instance, so nothing ambient is required — which matters because the SDK's toolchain
  is pinned to Java 11, where `ScopedValue` does not exist.
- **`dag.task(...)` is a factory method, not a constructor.** Java has no `new dag.TaskRef(...)`:
  qualified inner-class creation is spelled `dag.new TaskRef(...)`, which reads as compiler trivia
  rather than as a Dag definition.
- **`dag.task(...)`, `.config(...)`, `.before(...)`, and `.after(...)` are proposed additions.**
  Today's shipped `Dag` has only `addTask(id, definition)`, which returns the Dag rather than a ref;
  `.config(...)` is keyed to the Dag serialization schema.
- **`register` is one overloaded verb**: `register(Class<?>)` for an annotated class, `register(Dag)`
  for a built one, and `register(dagId, taskId, Class<? extends Task>)` for a stub handler
  ([ADR-0001](0001-mixed-lang-dag-interface.md)). It is proposed here; today a bundle is built from an
  `Iterable<Dag>` through `BundleBuilder.getDags()`.
