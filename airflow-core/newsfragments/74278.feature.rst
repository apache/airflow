Plugin external views and React apps can be scoped with an optional ``applies_to`` block: a map of dotted field path to the values that path may take, such as ``{"state": ["failed"], "dag.tags.name": ["ml"]}``. Any field the REST API returns for the entity is addressable, so a tab or panel appears only where it is relevant instead of on every Dag. An unqualified path is rooted at the entity the ``destination`` is about; a path may instead name a related record (``dag``, ``dag_run``, ``task``, ``task_instance``) as its first segment, and traversing a list fans out across it. Values are OR-ed within a path and AND-ed across paths, and a path whose root record the current page cannot resolve is skipped rather than failing the match, so one block can be shared across a plugin's Dag- and task-level destinations. Omitting ``applies_to`` shows the item everywhere, which is the previous behaviour. This replaces the five fixed criteria (``dag_tags``, ``dag_ids``, ``task_ids``, ``operators``, ``operator_names``) added earlier in this development cycle and never released, so there is no deprecation path: ``dag_tags`` becomes ``dag.tags.name``, ``dag_ids`` becomes ``dag.dag_id``, ``task_ids`` becomes ``task_id``, and both operator criteria become ``operator_name``. The trade is that paths are resolved against the API response rather than checked against a fixed vocabulary: a path naming no field is logged with a suggested correction when plugins load, but one below a field the response models do not describe (such as ``class_ref``) cannot be checked, and widens the scope instead of narrowing it. Matching is equality-only. See :doc:`the plugins documentation </administration-and-deployment/plugins>` for details.
