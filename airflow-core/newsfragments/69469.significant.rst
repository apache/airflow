psycopg3 is now the default sync Postgres driver, with statement preparation disabled

``psycopg`` (psycopg3) is now the default synchronous Postgres driver for the metadata database, mirroring the existing async default. A bare ``postgresql://``, or a legacy ``postgres://`` or ``postgres+psycopg2://``, ``sql_alchemy_conn`` is now rewritten to ``postgresql+psycopg://`` instead of ``postgresql+psycopg2://``, while an explicit ``postgresql+psycopg2://`` connection string is left untouched. Install the ``apache-airflow-providers-postgres[psycopg2]`` extra to keep using psycopg2.

Airflow also sets ``prepare_threshold = None`` on both the sync and the async psycopg3 engine, which disables psycopg3's automatic server-side statement preparation.

**Why:** psycopg3 prepares a statement server-side once it has been executed ``prepare_threshold`` times (5 by default). A pooler running in transaction mode routes consecutive transactions on one client connection to different server connections, so unless it tracks prepared statements itself, queries begin failing with ``InvalidSqlStatementName`` -- or ``DuplicatePreparedStatement`` where several clients generate the same statement name -- once the threshold is crossed. The Airflow Helm chart sets ``pool_mode = transaction`` and ships PgBouncer 1.23.1 without setting ``max_prepared_statements``, so the recommended deployment is one of the affected ones. Preparation is turned off outright rather than only having its threshold raised, so Postgres re-parses each statement and bulk ``executemany`` writes no longer reuse a single prepared statement.

No released version selected psycopg3 by itself, so this takes nothing away from an existing default installation. Deployments that already point ``sql_alchemy_conn`` or ``sql_alchemy_conn_async`` at ``postgresql+psycopg://`` or ``postgresql+psycopg_async://`` explicitly will stop preparing statements on upgrade.

**To keep statement preparation** you need both halves; restoring ``prepare_threshold`` alone will reintroduce the failures above unless the pooler can handle it.

First make the pooler safe for it. With PgBouncer that means 1.22 or newer, ``max_prepared_statements`` set above 0 (it defaults to 0 until 1.24, where it becomes 200), and ``libpq`` 17 or newer on the Airflow side -- see `the psycopg documentation <https://www.psycopg.org/psycopg3/docs/advanced/prepare.html#using-prepared-statements-with-pgbouncer>`_. Running without a pooler at all is also fine.

Then put the setting back, by pointing ``sql_alchemy_connect_args`` at a dictionary defined in your ``airflow_local_settings.py``:

.. code-block:: ini

    [database]
    sql_alchemy_connect_args = airflow_local_settings.PSYCOPG3_CONNECT_ARGS

.. code-block:: python

    PSYCOPG3_CONNECT_ARGS = {"prepare_threshold": 5}

Anything set there is merged over the default and wins. The same applies to ``sql_alchemy_connect_args_async`` for the async engine.
