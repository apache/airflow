AIP-125: Inbound webhooks (experimental)

Airflow can now receive webhooks from services such as GitHub. It verifies each delivery with a secret shared with the sender, records it, and acts on it in three ways: it records an asset event on each of its topic names that a Dag schedules on, which starts a run of that Dag; it records an event on each data asset that an asset route in the webhook's connection names for it; and it resumes the tasks whose webhook waits it matches. Dags subscribe by scheduling on ``airflow.sdk.WebhookTopic``. Tasks wait with ``WaitForWebhookOperator`` or ``@task.webhook_wait`` from the standard provider, or with ``BaseOperator.wait_for_webhook`` in an operator of their own: the task parks in the ``awaiting_input`` state, without a worker slot, a pool slot or a trigger, until a delivery matches the events and attributes it names or its timeout passes. The ``hmac_json`` and ``token_header`` source types ship in the standard provider, and ``github`` in the GitHub provider. The feature is experimental: its configuration, routes, responses, metrics, CLI commands, source type interface, match grammar and the events that waiting tasks resume with may change in a minor release.

The feature is opt-in. Only an API server started with ``airflow api-server --apps webhooks`` serves deliveries, ``--apps all`` stays ``core,execution``, and nothing is served until a webhook is listed in ``[webhooks] names``. Dags and existing APIs are unaffected, but these things change for every deployment:

- ``/webhooks`` is reserved. A plugin FastAPI app whose ``url_prefix`` starts with ``/webhooks``, such as ``/webhooks-legacy``, is skipped with a logged error, and the Core API Server answers ``/webhooks`` and every path under it with 404.
- ``airflow db migrate`` adds two tables: ``inbound_delivery``, which ``airflow db clean`` cleans by its ``retain_until`` column, and ``inbound_wait``, which it cleans by the ``deadline`` of each wait.
- The ``awaiting_input`` task state, which only Human-in-the-loop tasks used, also holds the tasks that wait for a webhook delivery. Tools that take every ``awaiting_input`` task for one awaiting a human response should check for a Human-in-the-loop request.
- The UI's **Browse** menu gains **Webhook Deliveries**, which lists the deliveries of every webhook whose connection the user may read, newest first and without their payloads, and has a **Webhooks** tab that shows whether each webhook can be served. The REST API lists the same through ``GET /api/v2/webhooks/~/deliveries`` and ``GET /api/v2/webhooks``, and a task instance's webhook waits through ``GET /api/v2/dags/{dag_id}/dagRuns/{dag_run_id}/taskInstances/{task_id}/webhookWaits``, which the task instance's **Details** tab shows. The Simple auth manager shows the menu entry to every user. The FAB auth manager shows it to users with menu access to Connections, as the ``Op`` and ``Admin`` roles have, once the FAB provider is upgraded to a release that maps the entry to Connections. With the Keycloak auth manager, run ``airflow keycloak-auth-manager create-resources`` again when you upgrade: until Keycloak has a resource for the new entry, it refuses the UI's menu authorization request, and the menus fail to load for every user.

A delivery's outcome tells what it did: ``resumed_wait`` if it went to a webhook wait, ``accepted`` if it recorded topic or asset route events, ``early`` if it did neither but has a correlation key, ``dag_paused`` or ``no_subscribers`` otherwise, and ``expired`` for an early delivery that newer ones pushed out. A delivery with a correlation key, such as each ``github`` delivery about a pull request or an issue, that nothing acts on is kept, with its payload, for a webhook wait registered within ``[webhooks] early_delivery_ttl`` seconds, so it shows as ``early`` rather than ``dag_paused`` when only paused Dags subscribe to it. A sender's redelivery of an ``early``, ``expired``, ``dag_paused`` or ``no_subscribers`` delivery is processed again in full, so a Dag unpaused since still receives it, unless a wait has taken the delivery meanwhile; a redelivery of an ``accepted`` or ``resumed_wait`` delivery is answered as a duplicate.

Tasks register their webhook waits through a new Execution API route. Upgrade the API servers before the workers: a task that waits through an older API server fails with ``WebhookWaitUnsupported``. The API servers that serve the Execution API check each wait against their own ``[webhooks]`` options and ``webhook_<name>`` connections, so give them the same options and access as the webhooks process, and the providers that ship the webhooks' source types. A wait registered without a timeout uses ``[webhooks] default_wait_timeout``, and is refused when that is not set. Webhooks have no team in Airflow 3.5: with multi-team on, topic events, asset routes and webhook waits serve only Dags without a team.

Users of the ``airflow-provider-inbound-webhooks`` proof of concept:

- Uninstall the package. Airflow skips its plugin app, its ``inbound_webhook`` connection form takes precedence over the standard provider's while it is installed, and versions of it that add an ``airflow webhooks`` command group make every ``airflow`` command fail.
- Move the ``[inbound_webhooks]`` options to ``[webhooks]`` by hand, renaming ``webhook_names`` to ``names``. Airflow reads no alias for the old section, and ``names`` does not accept ``*``.
- Delivery records are not carried over, so a sender's retry of a delivery received just before the switch is processed again.
- Topic names are unchanged for ``github``, ``hmac_json`` and ``token_header`` as long as their values are ASCII: the package folded other characters to ASCII, while Airflow offers no name for a part that has them. Airflow 3.5 has no ``gitlab`` or ``jira`` source type.
- Topic events leave out payloads larger than ``[webhooks] max_event_payload_bytes``, 65536 bytes by default. Set it to ``0`` to copy every payload, as the package does by default.
- Import ``WebhookTopic`` from ``airflow.sdk``, and give the branch of a push as its ``action``.
