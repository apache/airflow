AIP-125: Cancelling runs and tasks from inbound webhooks (experimental)

Dags and tasks can declare which deliveries to Airflow's inbound webhooks cancel their runs, with ``cancel_on=[WebhookMatch(...)]``, ``WebhookMatch`` being a new class in ``airflow.sdk`` that names a webhook, events and attributes with the grammar of webhook waits. Only a delivery with a correlation key cancels: it records a cancel request for each Dag whose conditions it matches, and the scheduler applies the request, within a second or two of the delivery's answer, to the Dag's queued and running runs that are about the key: the runs started from an event that an earlier delivery to the same webhook with the key recorded, and those queued before the delivery with the key in their conf under the condition's ``correlation_key_conf``. The scheduler also applies the request to a run that it creates later from an event that a delivery recorded before the cancelling one. A Dag's ``cancel_on`` fails those runs as marking them failed does, stopping their running tasks, whose ``on_kill`` runs, and runs the Dag's ``on_failure_callback`` with ``context["reason"]`` set to ``cancelled``, unless a teardown still has to run: such a run ends when its teardowns finish, ``failed`` with the reason ``task_failure`` or ``success``, as its leaf tasks make it end, and gets no ``cancelled`` callback; a task's ``cancel_on`` sets that task to its ``cancel_state``, ``failed`` by default or ``skipped``, and the run goes on. A cancel is a failure: Airflow has no cancelled state, and a cancelled run is ``failed`` and counts toward ``max_consecutive_failed_dag_runs`` when a later run fails. The scheduler applies up to ``[webhooks] cancel_requests_per_loop`` requests, 20 by default, each time it looks for them, about once a second, so a cancel waits while no scheduler runs. With multi-team on, no cancel is requested for a Dag with a team. The deliveries list their cancel requests with what the scheduler did with each, the Dag details and the task instance details show the conditions, ``airflow webhooks check`` lists them, the scheduler writes ``webhook_cancel`` audit log entries and emits the ``webhooks.cancels`` metric, and a cancelled run gets a note naming the delivery. The feature is experimental: ``WebhookMatch``, ``cancel_on``, ``cancel_state``, which runs a cancel request applies to and what it does to them may change in a minor release.

``airflow db migrate`` adds two tables: ``webhook_cancel_request``, which holds the cancel requests of deliveries and which ``airflow db clean`` cleans by the ``retain_until`` of their delivery, and ``dag_cancel_condition``, which holds the ``cancel_on`` conditions of Dags, which the Dag processor keeps in step with each Dag and which go with their Dag. A Dag that uses ``cancel_on`` needs this release in the Task SDK of the Dag processor and the workers as well as in Airflow core, so upgrade them together.

A delivery gets the new outcome ``cancel_requested`` when it recorded cancel requests but no topic or asset route events and went to no webhook wait. Such a delivery is kept for webhook waits as an ``early`` delivery is, and counts toward ``[webhooks] early_delivery_max_per_webhook``. When newer deliveries push it out, it becomes ``expired`` and its cancel requests stay. A redelivery of it is processed again in full, answered 202 ``cancel_requested``, and records no second cancel request for any Dag. Only ``accepted`` and ``resumed_wait`` redeliveries are answered as duplicates.

See :doc:`/authoring-and-scheduling/webhook-cancel` and :doc:`/administration-and-deployment/webhooks`.
